# Audit SmartDoc — 28 Oktober 2026

## Kesimpulan

Fondasi aplikasi dapat dikembangkan, tetapi belum layak diberi label production-ready. Ada bug fungsional yang dapat menghasilkan status sukses palsu, membuat UI penggabungan tertahan, menyisakan dokumen fisik setelah penghapusan, dan melemahkan pembatasan pemrosesan. Konfigurasi deployment dan dependensi juga membutuhkan perbaikan sebelum aplikasi dibuka untuk pengguna eksternal.

Audit menggunakan **working tree saat ini**, termasuk perubahan yang belum di-commit, bukan hanya HEAD Git. Sebagian temuan mencakup perubahan terbaru dalam sesi ini. Build dan tes kontrak yang lulus sebelumnya belum mencakup seluruh alur pengguna.

Prioritas: **P1** perlu ditangani sebelum rilis/penggunaan eksternal; **P2** perlu diselesaikan dalam stabilisasi sebelum menambah banyak fitur; **P3** meningkatkan keterawatan dan kualitas pengalaman pengguna. Prioritas berbeda dari label severity pada database advisory.

## Temuan P1

### A01 — Dependensi frontend memiliki advisory critical yang relevan untuk Windows

**Lokasi:** `smartdoc-frontend/package.json:17`, `package-lock.json`.

Next.js dipin ke `16.3.1`. Pemindaian npm menandai `next` critical serta `sharp`, `postcss`, dan `source-map-js` high. Advisory maintainer Next.js menyebut RCE pada server dengan filesystem Windows untuk rentang yang mencakup versi ini. Workspace saat ini berjalan di Windows; deployment Docker Linux memiliki kondisi paparan berbeda. Tidak ada exploit yang dijalankan dalam audit ini.

Advisory `next/og` juga dilaporkan scanner, tetapi kode aplikasi tidak ditemukan menggunakan `ImageResponse`; jangan menyamakan semua kecocokan versi dengan exploit yang dapat dicapai. Lakukan upgrade terencana sesuai advisory terbaru, review dependensi transitif, dan jalankan regresi build/fitur. Jangan menggunakan `audit fix --force` tanpa meninjau perubahan.

Sumber primer: [Next.js Windows RCE](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36), [Next.js ImageResponse advisory dan syarat paparannya](https://github.com/vercel/next.js/security/advisories/GHSA-vcvr-r3jv-pc5j).

### A02 — Dependensi backend pemroses input publik belum aman untuk rilis

**Lokasi:** `smartdoc-backend/requirements.txt`, khususnya `python-multipart==0.0.9`, `pypdf==4.1.0`, `pillow==10.2.0`, `python-jose==3.3.0`; virtualenv memuat `starlette==0.36.3`.

OSV menandai 12 package dalam virtualenv: Mako, certifi, dnspython, ecdsa, pillow, pypdf, pytest, python-dotenv, python-jose, python-multipart, setuptools, dan starlette. Ini mencakup dependency transitif dan tooling; kecocokan advisory perlu ditriage per penggunaan, bukan dianggap 12 exploit yang terbukti.

Satu kasus relevan sudah terkonfirmasi dari advisory maintainer: `python-multipart <0.0.18` memiliki DoS saat memproses multipart. Batas ukuran dalam handler aplikasi berjalan setelah parsing multipart oleh framework, sehingga tidak menggantikan patch parser atau batas request di ingress. Upgrade FastAPI/Starlette/multipart serta engine PDF/gambar secara kompatibel dan ulangi pengujian file.

Sumber primer: [python-multipart DoS](https://github.com/Kludex/python-multipart/security/advisories/GHSA-59g5-xgcq-4qw3). Hasil OSV merupakan pencocokan versi terhadap database advisory, bukan bukti eksploitasi aplikasi.

### A03 — Dependensi wajib `reportlab` tidak tercantum dalam instalasi backend

**Lokasi:** `app/services/watermark/pdf.py:6`, `app/main.py:23`, `requirements.txt` (path backend).

Router watermark mengimpor ReportLab pada startup, tetapi manifest tidak mencantumkannya. Virtualenv lokal memiliki ReportLab 5.0.1 dengan `Required-by` kosong; lingkungan lokal menutupi ketergantungan yang tidak dideklarasikan. Instalasi bersih berdasarkan manifest berisiko gagal saat import aplikasi, termasuk semua endpoint lain, bukan hanya watermark.

Tambahkan dependency eksplisit yang kompatibel dan uji startup dari lingkungan bersih. Belum dilakukan clean image build untuk mengonfirmasi seluruh dependency container.

### A04 — Deployment frontend Docker tidak konsisten dengan topologi service

**Lokasi:** `docker-compose.yml:7`, `smartdoc-frontend/next.config.ts:14`, `smartdoc-frontend/Dockerfile:9` dan `:23`.

Compose memberikan backend URL default `http://localhost:8000`; nilai publik di `.env` lokal juga demikian. Rewrite Next.js berjalan di server frontend: di Docker, localhost mengarah ke container frontend sendiri. Login dan semua `/api/*` akan gagal kecuali URL diubah ke alamat service yang dapat dijangkau, misalnya `http://backend:8000`.

Selain itu, runner menyalin `/app/public`, sementara tidak ada file `public/` yang tercatat di Git. Folder kosong lokal tidak ikut clone bersih, sehingga langkah COPY tersebut dapat gagal. Frontend juga belum mempunyai `.dockerignore`: `COPY . .` dapat mengikutkan `node_modules`, `.next`, dan file environment lokal, memperbesar context serta berisiko membawa artefak host ke build Linux.

Pisahkan konfigurasi backend internal dari URL publik, buat build context terkontrol, dan buktikan build dari checkout bersih.

### A05 — Timeout job tidak menjamin engine/subprocess berhenti

**Lokasi:** `app/api/converter.py:110`, `app/api/merger.py:66`, `app/api/watermark.py:67`, `app/services/converter/office.py:87`, `app/services/compressor/pdf.py`.

Worker memakai `asyncio.wait_for`, sedangkan subprocess helper hanya menangani timeout internalnya. Ketika timeout luar membatalkan coroutine helper, `CancelledError` tidak ditangani untuk kill/wait subprocess. Reproduksi dengan subprocess mock menghasilkan `subprocess_kill_called=false` setelah timeout job.

Untuk engine yang memakai `asyncio.to_thread`, pembatalan await juga tidak menghentikan pekerjaan thread. Akibatnya job bisa ditandai gagal dan semaphore dilepas sementara engine masih memakai CPU, file, atau proses eksternal. Cleanup dapat berlomba dengan engine yang belum berhenti.

Tetapkan satu mekanisme deadline/cancel yang benar-benar menghentikan proses kerja. Tangani cancellation subprocess dengan `finally` yang terkontrol; untuk pekerjaan yang membutuhkan hard timeout, gunakan proses worker yang dapat dihentikan dan di-reap.

### A06 — Semaphore LibreOffice dipakai dari event loop berbeda

**Lokasi:** `app/services/converter/office.py:69` dan `:120`, `app/services/merger/pdf.py:21`, `app/services/watermark/pdf.py:87`, `app/api/documents.py:127`.

Helper sinkron membuat thread dan menjalankan `asyncio.run`, tetapi converter asinkron memakai `libreoffice_semaphore` global yang juga dipakai event loop API. Semaphore asyncio bukan pengunci lintas thread/event loop. Saat jalur preview, merger, watermark, dan converter berjalan bersamaan, contention dapat menyebabkan error loop atau antrean tidak terselesaikan.

Temuan berdasarkan jalur kode; belum dilakukan stress test lintas loop pada LibreOffice asli. Satukan eksekusi LibreOffice pada satu loop/worker atau gunakan mekanisme pengunci yang sesuai batas proses/thread. Tes semaphore saat ini hanya menjalankan mock di satu loop.

### A07 — Limiter default dan batas antrean belum melindungi endpoint pemrosesan

**Lokasi:** `app/core/limiter.py:7`, `app/main.py`, seluruh `/process`, `/info`, dan `/api/documents/first-page-preview`.

`default_limits=["120/minute"]` disetel, tetapi tidak ada SlowAPI middleware dan endpoint non-auth tidak didekorasi limiter. Reproduksi 130 request berturut-turut pada endpoint documents menghasilkan **0 respons 429**. Pembatasan login/register yang didekorasi tetap terpisah dan tidak boleh dianggap hilang.

Semaphore membatasi job yang sedang berjalan, bukan jumlah upload, antrean, user, atau ruang disk. Preview/info juga dapat melakukan konversi/render tanpa job semaphore. Pengguna yang dapat mendaftar sendiri dapat menumpuk upload/job dan pekerjaan preview.

Terapkan rate limit pada jalur mahal, batas jumlah job queued per akun/global, kuota storage, dan admission control sebelum menyimpan input. Uji di balik proxy agar identitas IP klien tidak tertukar menjadi IP frontend.

### A08 — Batas dokumen tidak diterapkan konsisten di semua fitur

**Lokasi:** `app/api/merger.py:164`, `app/api/splitter.py:185` dan `:238`, `app/api/watermark.py:105`, `app/api/documents.py:86`.

Converter/compressor memanggil validasi batas 50 halaman PDF; splitter, merger, watermark dan preview tidak memakai kebijakan yang sama. Merger hanya membatasi minimum dua file; `total_input_size` dihitung tetapi tidak dibatasi. Office yang berubah menjadi PDF juga tidak konsisten diperiksa jumlah halaman hasilnya.

Batas 35 MB per file tidak membatasi jumlah halaman, total file dalam satu merger, ukuran halaman render, atau total beban permintaan. Terapkan validasi bersama pada input dan PDF kerja serta batas total file/byte/halaman. Tolak dokumen terenkripsi secara konsisten sebelum menjadwalkan engine.

### A09 — Container Office dan gambar embedded belum memiliki batas dekompresi

**Lokasi:** `app/core/validators.py:119`, `app/services/compressor/office.py:50`, `app/services/compressor/office.py:16`.

Validasi Office hanya menerima signature ZIP/container; belum memeriksa struktur DOCX/XLSX/PPTX, total ukuran setelah ekstraksi, compression ratio, atau jumlah entri. Compressor membaca tiap entri ke RAM dengan `zin.read`. Validasi dimensi untuk gambar upload langsung tidak diterapkan pada gambar embedded.

ZIP kecil atau gambar embedded yang besar dapat memakai RAM/CPU jauh melampaui ukuran upload. Tambahkan pemeriksaan struktur dan batas dekompresi, serta jalankan parser dokumen dengan batas resource. Tidak dilakukan pengujian ZIP bomb yang berpotensi menghabiskan resource host.

### A10 — Dokumen gabungan meninggalkan input fisik tanpa kepemilikan lengkap

**Lokasi:** `app/api/converter.py:261`, `app/api/merger.py:210`, `app/api/documents.py:286`, `app/core/cleanup.py:17`.

Multi-image converter dan merger menyimpan semua input ke `documents/originals`, tetapi Document hanya merekam `input_paths[0]`. Hapus dokumen hanya menghapus original pertama dan output. Cleanup TTL hanya memindai `temp`, sehingga original kedua dan seterusnya tetap tersimpan tanpa record yang dapat dikelola pengguna.

Kegagalan validasi input berikutnya atau DB commit setelah penulisan file juga dapat meninggalkan input tanpa record. Ini masalah privasi/retensi sekaligus pemakaian disk, bukan sekadar file sementara.

Gunakan manifest/relasi input per document atau folder job yang dapat dibersihkan utuh. Jadikan tahap upload sementara, validasi, commit, dan cleanup eksplisit, termasuk jalur gagal.

### A11 — Compressor dapat mengembalikan sukses tanpa output

**Lokasi:** `app/api/compressor.py:62` sampai pembaruan status sesudahnya.

Hasil engine disimpan dalam `success`, tetapi worker langsung menandai job dan document `done` tanpa memastikan output tersedia. Reproduksi engine `False` tanpa file menghasilkan `job=done`, `document=done`, `output_exists=false`.

`False` pada engine saat ini juga dapat berarti file sudah optimal dan original disalin. Jangan mengubah semua `False` menjadi gagal: perlu kontrak hasil yang membedakan compressed, unchanged-with-valid-output, dan failed. Sukses wajib mensyaratkan output valid.

### A12 — Penghapusan dapat berlomba dengan job aktif dan commit database

**Lokasi:** `app/api/documents.py:276` dan `:308`, seluruh worker `_run_*_job`.

Endpoint hapus menerima dokumen pending/processing dan menghapus job serta file tanpa cancel/lock. Worker masih dapat mengakses record yang telah hilang atau membuat output baru setelah record dihapus. Selain itu file dihapus sebelum DB commit; bila commit gagal, rollback database tidak mengembalikan file. Kegagalan penghapusan file ditelan lalu record tetap dihapus.

Terapkan aturan hapus/cancel untuk job aktif, status tombstone/deleting, dan cleanup yang dapat diulang. Bedakan kegagalan DB dari cleanup fisik dan tambahkan pengujian race delete-versus-worker.

### A13 — Kegagalan migrasi disembunyikan oleh fallback `create_all`

**Lokasi:** `app/main.py:55`, `app/db/base.py`, `alembic/versions/004_restrict_user_roles.py`.

Setiap kegagalan Alembic, termasuk constraint/data tidak cocok, ditangkap lalu startup menjalankan `create_all`. Fungsi tersebut tidak memperbarui tabel lama atau menambahkan CHECK constraint ke tabel yang sudah ada. Backend dapat tetap melayani traffic dengan schema yang tertinggal atau pembatasan role yang belum terpasang.

Untuk produksi, migrasi harus menjadi gate yang gagal secara jelas. Jalankan terkontrol sebelum readiness dan periksa revision/schema nyata. Jangan menganggap validasi SQL offline sebagai bukti migrasi berhasil pada data lama.

### A14 — Proteksi PDF mengklaim AES-128 tetapi menggunakan RC4-128

**Lokasi:** `app/services/watermark/pdf.py:114`, `README.md`, teks panduan keamanan.

`writer.encrypt(use_128bit=True)` tidak menyetel algoritma AES. Implementasi pypdf terpasang memilih `RC4_128` ketika parameter `algorithm` kosong. Reproduksi output menghasilkan encryption dictionary `/V=2`, `/R=3`, `/Length=128`, sesuai jalur RC4 tersebut.

Pilih algoritma eksplisit yang sesuai kebutuhan keamanan, verifikasi metadata serta interoperability hasilnya, dan sesuaikan teks UI/dokumentasi. Pengujian membuka PDF dengan password saja tidak membuktikan algoritmanya AES.

### A15 — UI merger tetap berstatus submitting setelah job selesai

**Lokasi:** `smartdoc-frontend/app/(user)/merger/page.tsx:78`, `:248`, `:880`.

Submit menyetel `isSubmitting=true`. Callback `onDone` dan `onFailed` tidak mengembalikannya menjadi false; modal memakai `isSubmitting || isPolling` sebagai kondisi terbuka. Job berhasil dapat meninggalkan modal di atas hasil serta tombol proses dalam keadaan disabled. Tombol close pada error hanya menghapus jobId, bukan status submitting.

Ini jalur kode yang deterministik, belum diuji dengan browser E2E. Turunkan status UI dari satu lifecycle job dan pastikan semua jalur done/failed/network-error/reset dapat keluar dari submitting.

## Temuan P2

### A16 — Penghitung riwayat selalu meminta limit di luar kontrak endpoint

**Lokasi:** `smartdoc-frontend/app/(user)/riwayat-dokumen/page.tsx:119`; backend `app/api/documents.py:50`.

FE meminta `limit=1000` untuk menghitung kategori, tetapi backend membatasi 100. Reproduksi mengembalikan 422. Karena kegagalan request penghitung tidak ditampilkan, kartu/tab dapat tetap menunjukkan nol walau tabel memiliki dokumen. Mengganti ke 100 pun tidak menghasilkan agregat akurat untuk arsip lebih besar.

Sediakan endpoint/agregat statistik milik akun di backend; pisahkan dari paginasi daftar.

### A17 — Error polling dan penutupan modal dapat meninggalkan state proses terkunci

**Lokasi:** `hooks/useJobPolling.ts:98`, halaman converter/splitter/watermark dan `components/ProcessingModal.tsx:69`.

Polling berhenti pada satu error jaringan/API, tetapi jalur ini tidak memanggil callback terminal. State `loading`/`isSubmitting` di halaman dapat tetap true. `onClose={() => setJobId(null)}` juga tidak mereset seluruh state. `stop()` hanya membersihkan timer; response request yang sedang berjalan masih dapat menjadwalkan poll berikutnya karena flag penghentian tidak disetel oleh stop.

Gunakan lifecycle tunggal, AbortController, retry terukur untuk error sementara, dan handler berhenti/error yang konsisten. Refresh/navigasi juga menghilangkan tracking job aktif tanpa mekanisme resume.

### A18 — Preview upload memiliki kebocoran Blob URL, race response, dan ketidaksesuaian jumlah halaman

**Lokasi:** `components/FileUpload.tsx:158`, `:185`, `:276`, `:291`; `app/api/documents.py:140`.

URL PDF/gambar yang dibuat untuk preview tidak direvoke saat file diganti, clear, atau unmount. Request preview tidak memiliki cancellation atau request identity, sehingga response file lama dapat menimpa file yang lebih baru. Response backend hanya memuat thumbnail halaman pertama, sedangkan UI menampilkan total halaman dokumen dan menawarkan pengalaman gulir halaman; Office tidak memiliki fallback native PDF seperti upload PDF.

Kelola lifecycle Blob/request dan nyatakan preview halaman pertama secara jelas atau sediakan rendering halaman sesuai kebutuhan. Hook `useFilePreview` yang baru sudah melakukan cleanup, tetapi komponen upload memakai jalur preview tersendiri.

### A19 — Race pada riwayat, paginasi setelah hapus, dan seleksi lintas halaman

**Lokasi:** `app/(user)/riwayat-dokumen/page.tsx:108`, `:220`, `:239`, `app/schemas/documents.py:8`.

Fetch pencarian/tab/halaman tidak punya cancellation atau pelindung response lama; respons lama dapat mengganti hasil filter terbaru. Setelah menghapus seluruh isi halaman terakhir, page tidak dikoreksi ke totalPages baru. Seleksi dapat bertambah lintas halaman tanpa batas 100, sementara batch endpoint sekarang menolak lebih dari 100 ID.

Tambahkan request identity/cancel, koreksi page, serta batas seleksi atau batch chunking dengan hasil per batch yang jelas.

### A20 — Lifecycle sesi belum konsisten di semua transport

**Lokasi:** `lib/AuthContext.tsx:49`, `:132`, `lib/api/files.ts:9`, `app/core/security.py:27`.

Error jaringan saat memulihkan profil menghapus token seolah sesi tidak valid. Transport JSON dan batch download mengarahkan 401 ke login, tetapi transport file hanya melempar error. Logout menghapus token browser tanpa pencabutan token server; token salinan masih berlaku sampai expiry tujuh hari selama akun aktif. Sinkronisasi login/logout lintas tab belum tersedia.

Definisikan kebijakan sesi, bedakan kegagalan jaringan dari 401/403, dan satukan handling expiry. Pertimbangkan sesi/cookie HttpOnly atau token lebih singkat dan revocation sesuai kebutuhan. Penyimpanan localStorage adalah pertimbangan hardening; audit tidak menemukan exploit XSS aplikasi yang terbukti.

### A21 — Beberapa parameter diterima tetapi tidak dihormati atau tidak divalidasi utuh

**Lokasi:** `app/api/merger.py:57`, `app/services/merger/pdf.py`, `app/services/splitter/pdf.py:11`, `app/api/watermark.py:105`, `app/schemas/documents.py`.

Mode insert menerima lebih dari dua file tetapi hanya memakai dua pertama; `after_page` di luar jangkauan dijepit ke akhir; parser range membuang token invalid dan tetap memproses bagian valid. Watermark tanpa teks/password diterima API walau UI melarangnya; opacity 0/1 diterima tetapi engine menjepit ke 0.05/0.9. Nama hasil saat pembuatan tidak memakai aturan RenameRequest: `custom_title` dapat mengandung separator/path traversal yang diteruskan ke nama entri ZIP batch.

Validasi kombinasi parameter dan nama hasil dengan schema yang sama, tolak input ambigu sebelum job dibuat, dan pastikan nama entri ZIP merupakan basename aman. Tambahkan tes kontrak untuk insert 3 file, range campuran invalid, dan custom title berseparator.

### A22 — Timestamp UTC kehilangan informasi zona waktu pada respons

**Lokasi:** `app/api/documents.py:423`, `app/api/jobs.py`, `app/(user)/riwayat-dokumen/page.tsx:53`.

Backend menyimpan UTC naive dan mengirim `isoformat()` tanpa `Z`/offset. Browser menafsirkan string itu sebagai waktu lokal. Di WIB, tampilan dapat bergeser tujuh jam dari kejadian sebenarnya.

Pertahankan standar penyimpanan yang dipilih, tetapi serialisasikan timestamp API sebagai UTC eksplisit. Uji FE di Asia/Jakarta dan zona lain.

### A23 — Gate kualitas dan cakupan tes belum cukup untuk menjamin alur utama

**Lokasi:** `eslint.config.mjs`, `tests/*.test.cjs`, `tests/conftest.py:7`, `tests/test_deep_verification.py:107`, konfigurasi CI.

Lint gagal dengan 22 error dan 23 warning: 12 error berasal dari `require()` di dua test CJS yang tidak dikecualikan oleh aturan TypeScript, sisanya mencakup `set-state-in-effect` dan `any`. Build sukses tidak menjalankan gate lint tersebut. Tes FE belum mengeksekusi komponen/alur login, upload, polling, download, atau modal.

Tes backend terisolasi lulus, tetapi suite integrasi bergantung pada user UUID tetap dan database eksternal, tanpa fixture database sementara dan startup/migration lifecycle yang lengkap. Tes anti-zombie menjalankan logika kill sendiri, bukan converter aplikasi, sehingga tidak mendeteksi A05. Belum ditemukan workflow CI di repository.

Tambahkan DB test terisolasi, jalankan migrasi di CI, tes engine/worker sebenarnya dengan batas resource, dan browser E2E untuk setiap alur fitur serta gagal/jaringan-putus. Pisahkan test tooling dari image runtime.

### A24 — Kontrak API belum menjadi satu sumber tipe yang dapat diverifikasi

**Lokasi:** `lib/api/types.ts`, `lib/api/watermark.ts`, `app/core/response.py`, router `/process` dan documents.

Sebagian besar endpoint memakai JSONResponse manual tanpa response model terstruktur; OpenAPI belum mendeskripsikan payload fitur secara lengkap. FE memelihara tipe sendiri; contoh `has_password` dinyatakan wajib dalam respons watermark FE tetapi tidak dikirim backend. Parameter filter feature dan nama hasil juga belum memakai schema domain bersama. Login memiliki bentuk OAuth2 yang berbeda; perbedaan ini sah tetapi harus terdokumentasi.

Tetapkan model request/response per resource, model lifecycle job, kode error stabil, serta pengujian kontrak. Setelah schema stabil, tipe FE dapat diturunkan dari OpenAPI.

### A25 — Readiness dan kebijakan konfigurasi produksi belum memadai

**Lokasi:** `app/main.py:157`, `app/core/config.py:39`, `docker-compose.yml:43`, `seed_user.py:19`.

Health selalu healthy tanpa memeriksa DB, ruang storage, atau ketersediaan engine. Validasi SECRET_KEY produksi hanya menolak satu literal default, sehingga kosong/nilai lemah lain tidak ditolak. Compose memakai kredensial DB tetap dan mengekspos port database. Script seed tanpa argumen memiliki password admin yang diketahui dan dapat menyinkronkan role existing user tanpa `--update`.

Ini risiko konfigurasi/operasional; audit tidak menyimpulkan akun default sudah ada di database. Buat readiness terpisah, validasi konfigurasi produksi dengan ketat, provisioning admin eksplisit, secret dari environment yang dikelola, akses DB internal, dan prosedur backup/restore yang diuji. Workspace saat ini memakai APP_ENV development; jangan menganggapnya konfigurasi deployment publik.

## Temuan P3 dan utang arsitektur

### A26 — Pemisahan modul belum menjangkau state fitur dan worker

FE telah membagi API transport dan hook, tetapi converter/riwayat/merger/splitter masih berupa halaman ratusan hingga lebih dari seribu baris; upload sekitar 823 baris nonkosong. State form, operasi API, preview, modal dan JSX saling terikat. Backend juga menggabungkan HTTP controller dan worker dalam router, dengan lifecycle status/cleanup yang berulang.

Ekstrak hook per fitur, subkomponen hasil/preview/tabel, formatter dan limit bersama. Pisahkan job runner dari router dan tetapkan satu state machine agar perbaikan gagal/cleanup tidak harus disalin lima kali. Tidak perlu mengganti framework atau melakukan rewrite total.

### A27 — Aksesibilitas dan konsistensi desain perlu peninjauan browser

Dropzone berbasis div klik dan input tersembunyi belum menyediakan aktivasi keyboard yang setara. Modal umumnya belum memiliki semantic dialog, focus trap dan pengembalian fokus. Tombol di dalam tautan download menghasilkan nested interactive elements. Beberapa komponen masih memakai warna/gradient dan bobot heading di luar DESIGN.md; label riwayat juga menyisakan `watermark, .`.

Perbaiki keyboard/fokus/semantic element, lalu lakukan pengujian responsif, kontras, dan pembaca layar. Temuan ini berasal dari inspeksi kode; belum dilakukan validasi visual/browser.

### A28 — Dokumentasi dan lifecycle schema lama perlu keputusan eksplisit

PRD/project masih memuat uraian OCR/template historis dan klaim production-ready/tes penuh, sedangkan dokumen arsitektur baru lebih sesuai kode. Migrasi historis mempertahankan schema OCR, model aktif menghapus field tersebut; belum ada rencana backfill/purge arsip legacy. `documents.user_id` masih nullable, sehingga arsip sebelum autentikasi dapat tetap tanpa pemilik dan tidak terlihat oleh query privat.

Tetapkan dokumen spesifikasi aktif, arsipkan catatan lama, inventaris data legacy, serta rencanakan migrasi/retensi dengan backup. Jangan menulis ulang migrasi lama atau menghapus data pengguna otomatis. Banyak file penting juga masih untracked/modified: audit menilai snapshot lokal; perubahan perlu masuk commit yang dapat direproduksi sebelum rilis.

## Hal yang sudah baik

- Login user dan admin memiliki endpoint berbeda dan ditolak jika role tidak cocok; registrasi publik tidak menerima role admin.
- Otorisasi memakai akun aktif dan role terbaru dari database, bukan hanya claim role JWT. Query dokumen/batch serta status job menerapkan kepemilikan akun.
- Pengunduhan dan preview hasil memakai Bearer token; pembacaan file download/preview/batch memiliki pemeriksaan containment storage.
- SQLAlchemy memakai parameter query, tidak ditemukan penyusunan SQL mentah dari input pengguna pada endpoint yang ditinjau.
- Ada pembatasan file per kategori, pemeriksaan signature, validasi dimensi gambar langsung, dan mekanisme fallback kompresi yang mempertahankan file asli jika tidak lebih kecil.
- Struktur API FE lebih terpisah, layout pengguna mengikuti route group, dan build TypeScript berhasil.

Poin-poin tersebut adalah hasil inspeksi kode dan tes terbatas, bukan pernyataan bebas celah keamanan.

## Urutan stabilisasi yang disarankan

1. **Keamanan dan deploy:** A01–A04, A07–A09, A13–A14. Gate: instalasi/build bersih, migration fail-fast, dependency triage, batas request/queue, verifikasi algoritma PDF.
2. **Kebenaran lifecycle:** A05–A06, A10–A12, A15–A19. Gate: output/status konsisten; timeout/cancel/delete tidak meninggalkan pekerjaan atau dokumen; semua modal dapat selesai/ditutup.
3. **Kontrak dan sesi:** A20–A25. Gate: FE/BE memakai kontrak yang sama, timestamp benar, sesi konsisten, readiness dan tes integrasi tersedia.
4. **Keterawatan dan pengalaman pengguna:** A26–A28. Gate: modul fitur lebih kecil, akses keyboard diuji, spesifikasi/data legacy diputuskan, commit rilis dapat direproduksi.

Tidak ada perubahan source aplikasi atau upgrade dependency yang diterapkan sebagai bagian audit ini. Artefak audit dan reproduksi ditambahkan agar temuan dapat ditindaklanjuti secara terukur.
